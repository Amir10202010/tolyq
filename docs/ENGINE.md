# TOLYQ — расчётное ядро

Документация к `src/core/*`. Интерфейс живёт отдельно и знает о ядре
только то, что записано в `src/core/types.js`.

## Что решает система

Отправитель с партией 8 тонн берёт фуру и везёт её заполненной на 40 %,
потому что вагон вмещает 68 тонн и в одиночку он его не наберёт.
Деньги и топливо горят на неделимости партии.

Ядро решает две связанные задачи одновременно:

1. **Каким маршрутом и каким транспортом везти** — многокритериальная
   задача на мультимодальном графе. Одного лучшего ответа нет, есть
   фронт Парето по стоимости, времени и выбросам.
2. **Когда отправлять** — задача оптимальной остановки: ждать ли ещё час,
   пока подъедет попутный груз, или отправлять сейчас.

## Запуск

Ни сборки, ни зависимостей, ни сети.

```bash
python3 tools/serve.py
```

Обычный `python3 -m http.server 8000` тоже работает, но браузер кэширует
ES-модули очень цепко: после правки исходника раннер молча показывает
результаты старого кода. `tools/serve.py` отличается ровно одним —
отдаёт `Cache-Control: no-store`. На защите это не нужно.

Тесты — `http://localhost:8000/tests/run.html`. Если в системе есть Node,
те же тесты гоняются из терминала:

```bash
node tests/run.js
```

Раннера два намеренно: на защите гарантированно есть браузер, а Node
может не быть. В корне лежит `package.json` с единственным полем
`"type": "module"` — без него Node принимает `.js` за CommonJS и падает
на первом `import`. Зависимостей он не добавляет.

**Терминальный раннер не проверен**: на машине разработки Node не
установлен, все прогоны шли в браузере. Если Node у вас есть, запустите
`node tests/run.js` первым делом.

## Модули

| Файл | Что делает |
|---|---|
| `types.js` | Контракт между интерфейсом и ядром. Не меняется без согласования обоих. |
| `random.js` | Детерминированный ГПСЧ mulberry32. `Math.random()` в проекте запрещён. |
| `network.js` | Граф сети: 12 узлов, 17 коридоров → 30 рёбер, тарифы, вместимости, плотности. |
| `co2.js` | Выбросы. Фура относится на отправителя целиком, вагон делится по тонно-километрам. |
| `pareto.js` | Алгоритм Мартинса: фронт Парето по трём критериям плюс отброшенные варианты. |
| `market.js` | Неоднородный пуассоновский поток заявок, аналитические распределения, обучаемая модель интенсивности. |
| `stopping.js` | Марковский процесс принятия решений, итерация по ценности, Монте-Карло. |
| `packing.js` | Упаковка вагона: жадный FFD как база, имитация отжига как основной метод. |
| `explain.js` | Опциональный слой LLM. Полностью необязателен, у всего есть синхронный откат. |
| `solve.js` | Оркестрация и публичное API. |

## Публичное API

```js
import { solve, simulateArrivals, computeStopping, runMonth, getNetwork } from './src/core/solve.js';
```

| Вызов | Возвращает |
|---|---|
| `solve(request)` | `Solution` — фронт, отброшенные, рекомендация, политика, упаковка, экономия, объяснение |
| `computeStopping(request, seed)` | `StoppingPolicy` — пороговая кривая, ожидаемая стоимость, час отправки, вероятность |
| `simulateArrivals(request, horizonH, seed)` | `Arrival[]` — поток попутных заявок для анимации |
| `runMonth(from, to, seed)` | `MonthSummary` — прогон 30 дней по коридору |
| `getNetwork()` | `{ nodes, edges, transshipment }` для отрисовки графа |
| `modelInfo()` | сводка обученной модели интенсивности |

Все функции чистые и детерминированные: один и тот же вход с одним seed
всегда даёт один и тот же выход.

## Три алгоритма

### Маршрутизация: алгоритм Мартинса

Многокритериальный поиск кратчайших путей, label-correcting. Метка —
`{ узел, стоимость, часы, CO₂, режим, путь, перегрузки }`. В каждом
состоянии держим множество недоминируемых меток; метка A доминирует B,
если не хуже по всем критериям и строго лучше хотя бы по одному.

Состояние поиска — пара **(узел, вид транспорта)**, а не просто узел:
прибытие фурой и вагоном по-разному продолжается и по-разному стоит.
Число перегрузок входит в сравнение четвёртым критерием: это ресурс,
и метку с меньшим числом перегрузок вытеснять нельзя.

Свёртку критериев весами применяем **к готовому фронту**, а не до поиска.
Взвешенная сумма находит только вершины выпуклой оболочки: маршруты
в вогнутых участках — как раз интересные мультимодальные компромиссы —
не выбираются ни при каких весах.

Отброшенные маршруты возвращаются отдельно: интерфейс рисует их серым,
и видно, что перебор был честным.

### Отправка: марковский процесс принятия решений

Формально:

- **Состояния** `S = {(t, q)}` — прошло `t` часов, накоплено `q` тонн
  (дискретизация по 2 т, 35 состояний).
- **Действия** `A = {ОТПРАВИТЬ, ЖДАТЬ}`; в терминальном часу допустимо
  только ОТПРАВИТЬ.
- **Функция переходов** — `transitionKernel()`: приход за час берётся
  из аналитического распределения `market.js`. Партия неделима: не
  влезла — состояние не изменилось.
- **Издержки**: отправка `wagonCost · myTons / q`, ожидание — плата за час.
- **Уравнение Беллмана**
  `V(t,q) = min( dispatchCost(q), hold + Σ P(Δ)·V(t+1, q+Δ) )`.
- **Политика** имеет пороговую структуру: `π* = ОТПРАВИТЬ ⟺ q ≥ q*(t)`.

Решается итерацией по ценности обратной индукцией. Горизонт конечен,
поэтому один проход назад по времени даёт точный оптимум — итерировать
до сходимости не требуется.

**Вероятность собрать вагон считается независимо, методом Монте-Карло**:
500 прогонов реального потока с применением найденной политики. Два
метода не имеют общего кода за пределами `market.js`, поэтому их
согласие — взаимная проверка. Этой связкой найдены три реальные ошибки
(см. `DECISIONS.md`); сейчас расхождение 0,02–5 %.

### Упаковка: имитация отжига

Рюкзак с двумя ресурсами (масса, объём) плюс несовместимость химии
с продуктами. База — first-fit decreasing по убыванию массы. Основной
метод — отжиг от решения FFD: три хода (включить, исключить, обменять),
геометрическое охлаждение, 4000 итераций, критерий Метрополиса.

Замеренный выигрыш над жадным: **в среднем +11,9 процентных пункта,
максимум +35,2, улучшение на 180 наборах из 200, ухудшений ноль.**

## Флагманский расчёт: 8 т, Астана → Алматы

| | |
|---|---|
| Фура сегодня | 170 000 ₸ · 20 ч · 1030 кг CO₂ |
| Вагон в одиночку | 168 500 ₸ — то есть **железная дорога сама по себе ничего не даёт** |
| Доля в собранном вагоне | **34 476 ₸** · 43 ч · 245 кг CO₂ |
| Экономия против фуры | 135 524 ₸ (80 %) и 786 кг CO₂ |
| Выигрыш именно от консолидации | 168 500 → 34 476, в **4,9 раза** |
| Отправлять на | 8-м часу, ожидаемая загрузка 39 т из 54,5 |

Смысл проекта виден во второй и пятой строке: перевести груз на рельсы
недостаточно, разница с фурой в пределах погрешности. Экономия возникает
только когда вагон собран, а собрать его в одиночку нельзя.

## Тарифы

Часть ставок — реальные данные, собранные командой; остальное — оценки.
Найти всё, что ещё требует проверки:

```bash
grep -n "ЗАГЛУШКА" src/core/network.js
```

**Автотранспорт.** Тариф **не аддитивен по плечам**: Астана—Караганда
90 000 ₸, Астана—Алматы 170 000 ₸ — на остаток пути приходилось бы
76 ₸/км, ниже стоимости дизеля. Сквозной рейс это один наём машины,
а не два. Поэтому наблюдённые направления заведены отдельными рёбрами
со своей ценой за рейс, а не выводятся из ставки за километр.
Направления с данными: Астана—Караганда, Астана—Алматы, Алматы—Шымкент,
Актобе—Атырау, Алматы—Хоргос. Остальные — 440 ₸/км, медиана наблюдённых.

**Железная дорога.** Регулируемый тариф КТЖ: 0,00151 ₸/кг·км внутри
страны, 0,00502 ₸/кг·км на погранпереходах. В отличие от автомобильного,
аддитивен по плечам, поэтому составные маршруты считаются корректно.

**Главное допущение.** Ставка ₸/кг·км умножается на ВМЕСТИМОСТЬ вагона,
а не на массу груза: вагон продаётся вагоном, против минимальной весовой
нормы, и делит его стоимость консолидация. Вынесено отдельной константой
`RAIL_BILLED_BY_WAGON_CAPACITY`. Если бы КТЖ считала по фактической массе,
консолидация была бы не нужна и проект терял бы смысл.

Каждое ребро несёт `tariffSource` — источник числа, и `tariffSuspect`
для двух наблюдений, которые не сходятся со своими же исходными данными.

## Что ядро делает с вырожденными случаями

| Ситуация | Поведение |
|---|---|
| Недостижимый узел | Пустой фронт, `recommended: null`, объяснение называет причину. Не исключение. |
| Дедлайн меньше времени в пути | Поиск повторяется без срока, все варианты помечены `feasible: false`, объяснение предупреждает. |
| Груз тяжелее вагона | Считаем целые вагоны, консолидацию не предлагаем, политика вырождена с причиной. |
| Несовместимые типы груза | Химия не берётся к продуктам ни в упаковке, ни в накоплении. |
| Нет автодороги (Достык) | `truckBaseline: null`, экономия нулевая, маршрут всё равно строится. |
| Мусор от интерфейса | Нормализуется и зажимается в границы в одной точке `solve()`. |

## Бюджет времени

`solve()` вызывается интерактивно при каждом движении ползунков,
поэтому лимит — 300 мс. Фактически:

| Операция | Время |
|---|---|
| `solve()`, худшая пара узлов | ~5 мс |
| Фронт Парето, одна пара | <1 мс |
| MDP + 500 прогонов Монте-Карло | ~9 мс |
| Отжиг, 4000 итераций | единицы мс |
| `runMonth`, 30 дней | ~27 мс |
| Обучение модели, 10 плеч × 4 недели | ~2 мс |
| Все 227 тестов | ~1,7 с |

## Слой LLM

Полностью необязателен. Ключ читается из `localStorage` под именем
`TOLYQ_LLM_KEY` и в репозиторий не попадает.

- `parseRequest(text)` — свободный текст в `ShipmentRequest`. Сначала
  пробуется оффлайн-разбор регулярными выражениями; сеть трогается,
  только если он не справился. Ответ модели проходит ту же валидацию.
- `explainSolution(solution)` — живое объяснение; при любой неудаче
  возвращается фраза, собранная шаблоном из чисел решения.

Нет ключа, нет сети, таймаут, испорченный ответ — движок этого не
замечает. Оффлайн-работа продукта не зависит от слоя LLM ни в чём.
